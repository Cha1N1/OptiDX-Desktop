# Code quality review — 2026-10-17

Reviewed the current Desktop deployment, ownership, snapshot retention, worker,
component pruning, and update paths, with reference to the previous reviews.
The earlier seven fixes are present; the findings below concern interactions
that remain untested. This is not an exhaustive audit of every UI or upstream.

## Findings

### P1 — Compacted baselines lose originals overwritten in later operations

Locations: `optidx_desktop/backups.py:271–272,295–298`, with
`remember_baseline` at lines 84–87 and worker baseline creation before configure.

Compaction drops an unmanaged file if the first operation leaves it unchanged.
The baseline pointer then names `originals`, and subsequent compaction returns
immediately. Later jobs do not add newly overwritten originals to this baseline.
The Cyboman backend replacement does not retain a ledger original, so deleting
its temporary operation snapshot can erase the only recovery copy.

Reproduced with an existing `OptiScaler/amd_fidelityfx_upscaler_dx12.dll`:
take and finalize the unchanged initial baseline (the same snapshot lifecycle
used by Configure), then install Cyboman through the real `install_amd_dll`
function using a local fixture archive, finalize the second operation, and
uninstall/restore originals. The compact baseline had no files, and the original
AMD DLL was absent after removal. Default snapshot retention was used.

Fix: retain each newly overwritten foreign file before discarding its operation
snapshot, either through complete per-file ledger coverage or by merging new
originals into the compact baseline. Cover configure → install → remove and
adding a component after an unrelated initial installation.

### P1 — ReShade pruning bypasses original restoration and leaves stale ownership

Location: `backend/OptiDX.py:2398–2413`.

ReShade installation now records files in `channel:reshade`, but pruning still
unlinks the backend component paths directly. Unlike the adjacent OptiScaler
special case, it never calls asset removal. An explicitly replaced foreign
proxy is deleted without restoring its original, and the asset group remains.
The general update dispatcher can subsequently reinstall that pruned ReShade
group because it still appears installed in the asset ledger.

Reproduced by deploying ReShade over a foreign `dxgi.dll` with explicit foreign
replacement enabled, recording its backend component manifest, then running the
real `install_selected_components` with an empty selection and pruning enabled.
The original proxy was absent and `channel:reshade` remained in the ledger.
Its original blob still exists, so full asset removal can recover it; selective
pruning does not fulfill that contract.

Fix: remove the ReShade asset group through its verified restore operation and
clear the corresponding backend ownership consistently. Test both original
restoration and a subsequent update that must not reinstall the removed group.

### P2 — Cyboman replacement invalidates OptiScaler payload ownership

Locations: `optidx_desktop/core_payload.py:58–62` and
`backend/OptiDX.py:1538–1543`.

The core payload ledger owns every archive support file, including a bundled
`OptiScaler/amd_fidelityfx_upscaler_dx12.dll`. The Cyboman installer replaces that
file directly. Backend component ownership transfers, but the Desktop asset
ledger retains the old OptiScaler hash. A subsequent core update interprets this
legitimate replacement as an external edit and refuses to proceed.

Reproduced with a synthetic compatible OptiScaler archive containing the AMD
support DLL, followed by the real Cyboman installer with a different compatible
fixture DLL. Repeating `install_optiscaler_payload` raises
`Conflict: Managed file was edited outside the app:
OptiScaler/amd_fidelityfx_upscaler_dx12.dll`.

Fix: transfer ownership and original recovery information consistently between
the two systems, or model this replacement as a managed overlay. Do not simply
disable hash checks. Cover combined core/AMD installation and repeated updates.
