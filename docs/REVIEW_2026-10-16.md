# Code quality review — 2026-10-16

Scope: Desktop Python modules, bundled backend deployment/removal paths, worker
transactions, UI jobs and profiles, discovery, launching, downloads, and packaging
scripts. This is a source review with local validation, not a gameplay or upstream
compatibility certification. Historical review documents remain unchanged.

No application fixes, version changes, commits, or AppImage rebuild were made.
All reproductions used temporary folders and mocked download/extraction or failure
boundaries. No real games were changed or launched. The original OptiDX and
OptiScaler repositories were not changed.

## Findings

P1 means a high-priority correctness or file-preservation issue; P2 means a normal
priority functional defect. All seven findings below were reproduced locally.

### 1. P1 — OptiScaler copies archive entries without per-file ownership preflight

Location: `backend/OptiDX.py:1486–1495`; Desktop guard at
`optidx_desktop/channels.py:150–159`; snapshot selection at
`optidx_desktop/backups.py:20–40`.

The Desktop guard checks the injection proxy, then calls the original installer.
That installer copies every payload-root entry over the corresponding game path,
including merging directories, without checking each existing file for foreign
ownership, symlinks, or Windows capitalization conflicts. It also suppresses copy
errors. The protections in `assets.deploy` do not cover this path.

Reproduction: an existing unmanaged `notes.cfg` containing `user config` became
`archive config` after a simulated OptiScaler extraction supplied the same name.
The installer did not require replacement approval. Such an otherwise untracked
configuration file is outside the pre-operation snapshot selection, so a snapshot
is not a general guarantee of original-file recovery here. Directory payloads are
tracked by their top-level entry, while the final text manifest includes only
entries passing `isfile`, leaving another gap in recursive file tracking.

Suggested fix: stage the entire payload, enumerate its actual destination files,
preflight them with the same containment/capitalization/ownership rules used by
Desktop deployment, retain originals for every overwritten file, and propagate
write errors. Add integration coverage through the real installer, including
unmanaged nested files and symlinked destination directories.

### 2. P1 — Pruning direct HelixSR deletes its original DLL backup without restoring it

Location: `backend/OptiDX.py:2452–2468`; compare the restoration contract in
`optidx_desktop/helixsr.py:57–99`.

The targeted HelixSR removal understands the direct replacement layout, verifies
the retained original, restores it, and reconnects its previous owner. The generic
"Remove unchecked managed components" path instead deletes every HelixSR-owned
file, including the replacement DLL, metadata, and original backup. It never
performs the restoration represented by that metadata.

Reproduction: install direct HelixSR over an existing AMD DLL, then prune all
unchecked components. Both the original AMD destination and
`.optidx-helixsr-original.bin` were absent afterward. Retained operation snapshots
may permit manual recovery, but the successful prune operation does not fulfill
the restore contract. Selecting Cyboman FSR in the same operation is also rejected
before pruning when the direct HelixSR marker exists.

Suggested fix: share one direct-layout removal implementation between targeted
removal and pruning, preserving its checksum checks and ownership transfer. Test
pruning with a retained unmanaged original and an original owned by AMD FSR.

### 3. P1 — Removal reports success and discards tracking after a deletion fails

Location: `backend/OptiDX.py:2224–2240`; caller:
`optidx_desktop/backend.py:190–196`.

`uninstall_dir` catches file deletion errors, continues deleting its manifest and
marker, and returns `True`. The Desktop adapter relies on that return value to
raise an error and trigger worker rollback. A failed deletion can therefore leave
an active mod DLL behind with no backend ownership record, while the UI reports
successful removal.

Reproduction: inject `PermissionError` for removal of tracked `dxgi.dll` only.
`uninstall_dir` returned `True`, retained the DLL, and deleted `.optidx-files`.

Suggested fix: aggregate deletion failures, retain tracking for outstanding paths,
and fail the operation so the worker can restore a consistent snapshot. Test a
partial uninstall through the actual backend function, rather than only a backend
stub that raises an exception.

### 4. P2 — Core OptiScaler deployment does not validate the DLL machine type

Location: `backend/OptiDX.py:1497–1506`; compare
`optidx_desktop/downloads.py:158–178` and
`optidx_desktop/inspection.py:83–85`.

The core installer finds the first filename matching `OptiScaler*.dll` and moves
it into the injection-proxy name. It does not run the PE validation used by the
Desktop DLL manager. Archive-path validation for a custom OptiScaler package does
not validate the architecture of its payload either.

Reproduction: supply a valid x86 PE as `OptiScaler.dll` for an x64 game. The real
installer copied it into `dxgi.dll` and printed an installed-success message.
ARM64 and malformed payloads likewise lack a machine-type gate on this path.

Suggested fix: select exactly one compatible payload using the common PE parser,
reject incompatible or ambiguous candidates before writes, and validate the
standard backend ReShade path under the same contract. Test the core path with
x86, x64, ARM64, malformed, and multiple-candidate archives.

### 5. P2 — A managed DXVK installation makes the general update fail

Location: `optidx_desktop/features.py:423–425`; installer group:
`optidx_desktop/channels.py:201–219`.

DXVK is stored as `extra:dxvk`, so `update_features` routes it through
`deploy_extra(id='dxvk')`. That dispatcher accepts only keys in `EXTRAS`, which
does not contain DXVK. Its implementation is the separate `install_dxvk` function.

Reproduction: deploy a temporary `extra:dxvk` asset group and call
`update_features`. It raises `ValueError: Unknown extra component`. In a worker
update this aborts the job and rolls back its other changes.

Suggested fix: dispatch DXVK updates to their actual installer, reusing the
recorded source and respecting update exclusions. Cover a general update after a
successful custom DXVK installation.

### 6. P2 — Standalone ReShade updates are silently skipped

Location: `optidx_desktop/features.py:406–438`; worker routing:
`optidx_desktop/worker.py:88–108`.

Standalone ReShade is owned by `channel:reshade`. `update_features` has no branch
for this group. When it is the only installation, there is no `.optidx-files`
manifest, so the worker skips the core backend and then silently skips the
standalone asset as well. Update checks can still advertise a ReShade update.

Reproduction: create a standalone `channel:reshade` group, call `update_features`,
and observe that `install_reshade` is never invoked and the old DLL remains.

Suggested fix: route the group to `install_reshade`, honor component/group
exclusions, and make the result distinguish updated, unchanged, and skipped
components. Test the complete worker route without a backend manifest.

### 7. P2 — Manual launching from source cannot import the launch module

Location: `optidx_desktop/app.py:877–882`; existing absolute-path entrypoint:
`launcher.py`.

The source GUI sets the launch subprocess working directory to the game folder
and starts `python -m optidx_desktop.launch`. `run.sh` does not install the package
or export its source directory through `PYTHONPATH`. A normal source checkout
therefore loses the package import path in that subprocess. AppImage packaging
sets a package path, so that distribution route is not implicated.

Reproduction: execute the exact module invocation with `--help` from a temporary
game directory and no `PYTHONPATH`. It exits with `ModuleNotFoundError: No module
named 'optidx_desktop'` before any launch can occur.

Suggested fix: use the existing absolute-path `launcher.py` entrypoint, as copied
source wrappers already do. Verify the GUI subprocess route with a harmless test
command from an external temporary working directory.

## Architecture and maintainability

The code volume is appropriate for the feature scope. The main package and
bundled backend total 8,868 lines across 30 Python files at review time. File
ownership, snapshots, launch environment restoration, and queued game copies are
useful separations. The existing tests exercise meaningful failure cases.

The main structural risk is having two deployment/ownership implementations with
different guarantees: the Desktop asset ledger and the inherited backend copy
and manifest machinery. Several findings above arise at this boundary. Unifying
their safety contracts is more valuable than reducing line count or replacing
the UI framework.

Other maintainability concerns, not additional confirmed defects:

- String-based action/group dispatch is distributed across the worker, feature
  dispatcher, update dispatcher, catalog, and UI. An explicit operation registry
  could make missing update handlers visible during validation.
- The UI classes combine widget construction, persistence, queues, launch routing,
  and asynchronous callbacks. Extracting job control and profile storage would
  make integration tests easier without a broad UI rewrite.
- JSON readers often validate syntax but assume the expected schema afterward.
  Ownership and recovery metadata especially should distinguish missing,
  malformed, and unsupported records, rather than treating all read failures as
  empty defaults.
- Repeated filesystem scans run synchronously while refreshing game details.
  Snapshot creation also copies known DLLs broadly and retains backups without
  an evident retention policy. Measure large installations before optimizing;
  provide explicit verified cleanup before introducing automatic deletion.
- Dense semicolon-separated statements and swallowed backend I/O errors make
  recovery behavior harder to audit. Prefer explicit failure propagation around
  file mutations.

## Validation and limits

- `python3 -B -m unittest discover -s tests -q`: **165 tests passed**, 62.742 s.
- Fresh offscreen source startup completed successfully using a temporary data
  directory; the empty-library screenshot was visually inspected.
- Temporary-folder reproductions confirmed the seven findings, using synthetic
  PE fixtures, mocked network/extraction boundaries, and injected deletion errors.
- The passing suite does not cover these combinations sufficiently. In
  particular, component tests frequently replace the actual installers with
  stubs, which is useful for selection logic but cannot establish copy safety.
- Live downloads, gameplay, GPU behavior, other distributions, and a new AppImage
  build were not tested. Source-launch reproduction used `--help` and did not
  start a runner or game. No application code changed, so rebuilding was not
  required.

Recommended order: repair file-preservation/removal findings 1–3, enforce core
binary validation, fix both update routes, then fix the source launch entrypoint.
Add regressions at the backend/worker integration boundaries before considering
larger refactoring.
